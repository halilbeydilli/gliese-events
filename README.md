# @gliese-watch/events

[![CI](https://github.com/halilbeydilli/gliese-events/actions/workflows/ci.yml/badge.svg)](https://github.com/halilbeydilli/gliese-events/actions/workflows/ci.yml)

A registry of the EVM event signatures that mean "who controls this contract, or what it is
allowed to do, just changed": proxy upgrades, admin and owner handovers, Safe signers and
modules, timelock operations, AccessControl and AccessManager roles, pauses, vault governance
(MetaMorpho, Morpho Vault V2, Euler, Aave V3 and V4), Lido and Aragon, OP Stack and Arbitrum
roots of trust, stablecoin admin actions and Chainlink feed swaps. Each signature carries a
stable key, a category and a severity, and its `topic0` is derived from the signature at load
time, so the list is usable directly as an `eth_getLogs` filter. It also ships a strict decoder,
the synthetic `slot.*` keys a storage-diff poller emits for silent changes, and a registry of
role names resolved from their hashes. It is for anyone indexing control changes rather than
user activity: security and incident teams, risk curators, on-chain dashboards, and alerting
services that need one list to subscribe to and one vocabulary to phrase what fired.

## Usage

```ts
import { TOPIC0S, EVENTS_BY_TOPIC0, decodeWatchedLog, roleNameOf } from '@gliese-watch/events';

const logs = await client.getLogs({ address, topics: [[...TOPIC0S]], fromBlock, toBlock });
for (const log of logs) {
  const hit = decodeWatchedLog(log);               // null when the data does not decode strictly
  if (!hit) continue;
  const { key, category, severity } = hit.event;   // 'access.role_granted', 'access', 'high'
  const role = roleNameOf(hit.args.role);          // 'PAUSER_ROLE' or null
  const layouts = EVENTS_BY_TOPIC0.get(log.topics[0])?.length;
  console.log(key, category, severity, role ?? hit.args.role, layouts);
}
```

Install with `npm install @gliese-watch/events viem`. viem is the only runtime dependency; the
package is ESM and ships type declarations.

Exports: `EVENTS`, `EVENTS_BY_TOPIC0`, `TOPIC0S`, `severityRank`, `decodeWatchedLog`,
`SYNTHETIC_EVENTS`, `SYNTHETIC_EVENT_KEYS`, `ROLE_NAME_BY_HASH`, `roleNameOf`,
`ACCESS_MANAGER_ROLE_NAMES`, `accessManagerRoleName`, `VAULT_V2_SELECTOR_NAMES`,
`vaultV2SelectorName`, `vaultV2Gate`, and the types `WatchedEvent`, `DecodedEvent`,
`SyntheticEvent`, `Category`, `Severity`.

## How keys are assigned

- A key is `<family>.<snake_case>` and never changes once published: `proxy.upgraded`,
  `safe.removed_owner`, `vault.curator_set`, `rollup.config_updated`. Consumers phrase and route
  on the key, not on the event name.
- Severity is about what the emitter can now do, not how often the event fires. `critical`:
  the controller or the code changed, or a guard was removed (implementation, admin, owner,
  Safe owners and threshold, guard, singleton, curator, governor, oracle source, dispute-game
  implementation, a pause on a core contract). `high`: a change that gates or prepares one of
  those, or moves a risk parameter (pending owner, two-step requests, role grants, caps, LTVs,
  rate models, timelock scheduling). `info`: bookkeeping and reversals (executions of already
  scheduled operations, cancellations, fee recipients, queue order, labels).
- One key normally maps to one signature. Two signatures share a key only when they are the
  same fact with a different ABI layout: Safe 1.3 versus 1.4.1 indexing (`safe.added_owner` and
  five others decode both layouts), MakerDAO `File` overloads (`auth.file`, four types), the
  five pause dialects behind `pause.paused` / `pause.unpaused`, and umbrella keys where the
  variants only differ by which parameter was set (`vault.pending_revoked`, `vault.params_set`,
  `vault.fee_set`, `vault.cap_increased`, `vault.gate_set`, the Aave `lending.*_changed` keys,
  `rollup.config_updated` for SystemConfig and SuperchainConfig). The test suite lists these
  in `MULTI_SIGNATURE_KEYS` and fails if any other key spans two topic0s. The inverse never
  holds: a topic0 maps to exactly one key.
- A topic0 that several protocols share is registered once and described in protocol-neutral
  wording; `EVENTS_BY_TOPIC0` returns every layout for it and the decoder tries them in order,
  strictly, and returns the first that decodes.
- Silent changes have their own `slot.*` keys (`slot.implementation_changed`,
  `slot.safe_modules_changed`, ...) so that a storage diff and a log never share a key.
- `DecodedEvent.initAnchor` marks logs that look like construction (`Initialized(1)`,
  `SafeSetup`, `OwnershipTransferred` from the zero address, first `NewImplementation`). It is a
  hint, not a decision. OP Stack proxies are upgraded through a storage-setter implementation
  that resets the initialised slot, so every OPCM upgrade re-emits `Initialized(1)` and an
  intermediate `Upgraded` on contracts that are years old; whether a log is setup or a change
  must be decided from the contract's age, not from the shape of the log.

## What is deliberately not here

- User flows: transfers, approvals, deposits, withdrawals, borrows, swaps, Safe
  `ExecutionSuccess`, Morpho authorisations, ERC-7540 operators.
- Price and accounting updates: Chainlink `AnswerUpdated` (including custom feeds that reuse
  the signature), Uniswap and Balancer swap-fee changes, Yearn and Lagoon reporting, Lido
  rebases, LayerZero packets, Euler EVC account events, rollup batch and output events.
- Setup-only events (`SetSpoke`, `SetSpokeImmutables`, `CreateMetaMorpho`) and struct-heavy
  plumbing whose only content is fee or buffer tuning.
- Signatures we have not read from the canonical source. Nothing enters the registry from
  memory or from a decoded log alone.

The audited list of families that are still missing, and the structural limits of a
topic0-only view, is in [docs/COVERAGE-GAPS.md](docs/COVERAGE-GAPS.md).

## Verification

- The registry never stores a hash. Every `topic0` is computed at load by viem's
  `toEventSelector` from the parsed signature, so a typo in a signature can produce a topic0
  nothing emits, but never a wrong label on a real one. The same rule applies to role names:
  `ROLE_NAME_BY_HASH` is built from a list of strings hashed at load, and the tests assert that
  every entry except `DEFAULT_ADMIN_ROLE` is keyed by the keccak of its own name and that no two
  hashes share a name.
- `test/events.test.ts` pins the exact counts (265 signatures, 221 keys, 9 categories), asserts
  that each `(key, layout)` is unique and that no topic0 maps to two keys, re-derives the
  topic0 of every family added since 2026-09-18 as `keccak256` of the canonical signature string
  written out in the test, pins 32 byte-exact selectors, and round-trips encoded logs through
  `decodeWatchedLog` for the layouts that matter (Safe dual layouts, MakerDAO overloads, Aave V4
  tuples, Aragon `SetApp`, OP `ConfigUpdate`).
- Before a family landed, its topic0s were matched against live logs: MetaMorpho and EVault
  deployments, the UltraYield Core vaults and their factory (Vault V2), Aave V3 Ethereum core,
  the Lido Kernel and OP SystemConfig, and the Ethereum Core Hub / Main Spoke and Base Equities
  Hub / MAG7 Spoke for Aave V4 and the AccessManager. The sources read for each family are named
  in the comment above its block in `src/registry.ts`.

## Adding a family

1. Read the events from the canonical repository at a named tag or commit, not from a block
   explorer ABI. Write the signature out in full; user-defined value types become their
   underlying type (`Id` is `bytes32`), structs are declared inline so the topic0 is the struct
   keccak.
2. Append `[key, category, severity, description, ...signatures]` to `SPECS` under a
   `// ---- <family> (<date>) ----` comment that names the files read. Keep the description to
   one line and protocol-neutral where the signature is shared.
3. If a key deliberately spans several topic0s, add it to `MULTI_SIGNATURE_KEYS` in the test and
   say why in the comment.
4. In `test/events.test.ts`, bump the counts, assert category and severity for every new key,
   assert `keccak256(toBytes(signature))` for every new signature, pin at least one byte-exact
   topic0 you saw in a live log, and add a decode round trip for any non-trivial layout.
5. For role-based families, append the role name strings (the preimages, which are not always
   the constant names: Aave V3 hashes `POOL_ADMIN`, not `POOL_ADMIN_ROLE`) to
   `HASHED_ROLE_NAMES` in `src/roles.ts` and assert one member in `test/roles.test.ts`.
6. Run `npm run categories` and paste the table into this README; add a line to `CHANGELOG.md`.

## Who runs this

This is the event registry of [Gliese Watch](https://gliese.io), which watches these events on
Ethereum, Base, Arbitrum, Optimism, Polygon and BNB Chain and delivers them through
[@GlieseWatchBot](https://t.me/GlieseWatchBot) on Telegram, email and webhooks. Maintained by
Halil Beydilli. Issues and pull requests are welcome.
